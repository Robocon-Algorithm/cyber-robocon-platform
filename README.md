# BR 策略竞技场：在本机运行、用比赛包复盘

本版可直接运行两份 Python 策略，按同一个比赛时钟推进 BR，保存逐帧回放和逐件计分。默认 180 秒、每 100 ms 决策一次。请先跑通示例，再改一项策略选择，用同一场景的回放比较差别。规则、动作时间和地图假设以[上级方案](../README.md)与代码为准。

## 在 Windows 上开始第一局

安装 Python 3.11 或以上版本；从本目录运行，不需要安装第三方运行依赖。

```powershell
python -m robocon_sim demo --output runs/demo-first
python -m robocon_sim replay runs/demo-first
python -m robocon_sim serve --host 127.0.0.1 --port 8765 --trusted-code
```

用浏览器打开 `http://127.0.0.1:8765`。用不同队名分别上传 [stack_builder.py](examples/stack_builder.py) 和 [adaptive_raider.py](examples/adaptive_raider.py)，选择两份版本后创建单局或换边系列。队列显示已完成后，点击该局的比分打开回放。拖动时间轴或点击事件即可查看当时状态；最终得分从内核账本读取。首次策略练习可先比较两份基线何时完成第一座公共塔、何时取得资格，以及能否赶在终场前放球。

每个版本只提交一份 UTF-8 `.py` 文件，最大 256 KiB，定义一个直接继承 `brsdk.Strategy` 的类，实现同步的 `on_step(self, obs, api)`。上传会检查语法和入口并生成源码摘要，执行前仍由操作者审查。完整回调与动作接口见[策略接口](../02_Python接口与策略示例.md)。

要体验跨层建塔，上传 [`l1_reach_builder.py`](examples/l1_reach_builder.py) 和任一基线策略。该示例先拿预叠两箱，站在本方的 L1 指定作业位把箱体放到 L2，再取塔顶、显式越阶，最后到 L2 塔旁加顶。回放里看比分栏的队名、机器人载荷标记和跨层作业提示，可以区分「机器人在哪一层」与「塔建在哪一层」。

## 对照实验和排行榜

```powershell
python -m robocon_sim match --red examples/stack_builder.py --blue examples/adaptive_raider.py --output runs/my-match
python -m robocon_sim match --red examples/l1_reach_builder.py --blue examples/stack_builder.py --output runs/l1-reach-example
python -m robocon_sim series --red examples/stack_builder.py --blue examples/adaptive_raider.py --count 2 --output runs/my-pair
python -m unittest discover -s tests -v
```

每次单局或演示的 `--output` 请用新目录或空目录。系列使用自己的 SQLite 及尝试目录。命令行 `match` 和 `series` 可用 `--config 文件.json` 和 `--duration-ms` 自定义实验；例如 22000 ms 可快速看到开局供料与取料。命令行、网页单局以及自定义配置的网页系列均为训练，不更新 Elo。

只有网页默认 180 秒、100 ms 的换边双局和十局场景包计榜，创建时需要选双方当前激活版本。新上传不会改变已创建任务的冻结版本。换边交换策略，场地和供料继续绑定红蓝；十局由四组常规双局和一组故障双局组成。默认故障是红侧首批 TR 运箱上箱滑落，实际是否触发见结果。完整双局按胜负均值结算一次，Elo 初值 1000、K=24。平台故障重试一次，无法完整完成则作废；旧尝试不能覆盖新尝试。策略回调硬超限或连续三帧异常属于技术结果。

默认数据目录仍为 `data/l1-reach`。3 m/s 和放置减半的对局从同一数据库中的新一组 Elo 开始，已有队伍、代码版本、比赛记录和旧评级都保留，无需重新上传。已创建的比赛保留原参数；重启服务后创建新对战，才会使用新参数。旧比赛包可在网页看历史画面；如需用命令行核验旧包，可用[调整前的源码](../历史方案/platform-before-3mps.zip)。

## 比赛包能回答什么

| 文件 | 用途 |
|---|---|
| `manifest.json` | 核对双方源码、地图、参数、种子、故障配置、规则/SDK/协议版本及实现文件摘要。 |
| `commands.jsonl`、`events.jsonl` | 区分策略提交、裁判回执、异常和世界事件。 |
| `snapshots.jsonl`、`integrity.json` | 保存完整 100 ms 边界及终场状态；检查记录顺序和完整性。 |
| `score_ledger.json`、`result.json` | 核对逐件得分、破平、资格、放球、失败和故障状态。 |
| `series_report.json` | 按 A/B 汇总胜局、均分、资格与放球，常规和故障场景分别列出。 |

重演使用当时记录的决定和技术失败，复核世界状态和事件，不再次运行策略。实现摘要有差异时，先使用原版本代码；旧包可查看记录，但不能当作新版重演通过。资格与放球时间来自事件，未达成保留空值。空槽等待只统计 BR 在自家交接点、可控制且空闲空载、三个槽均空的帧，不能推断作者一定在等料；供料背压只统计批次进入 `waiting_slots` 的帧。恢复耗时从开始到对应恢复完成事件，仅统计已完成区间。

## 当前验证和使用边界

3 m/s 版本通过 77 项自动测试。同一组 `stack_builder.py`（红）对 `adaptive_raider.py`（蓝）各跑一场 180 秒：蓝方取得资格从 72.6 秒提前到 68.0 秒，中央放球从 178.5 秒提前到 162.8 秒，终场余量从 1.5 秒增加到 17.2 秒。两场都核验了 1800 帧重演。另一组 `l1_reach_builder.py`（红）对 `adaptive_raider.py`（蓝）中，蓝方在 167.2 秒才接球，终场未放球；提速后的策略仍要为交接槽和回程留时间。

调整前，跨层版通过 74 项自动测试。用 Chrome 上传跨层示例和 `stack_builder.py` 实跑换边双局：示例在红方时于 20.9 秒从 L1 放下整摞、51.8 秒在 L2 加顶；在蓝方时分别为 18.9 秒和 49.8 秒。两局均核对队名、载荷标记和终场账本。另在首批上箱滑落的场景实跑，示例先从 L1 放塔基，再从 L1 补中段，最后在 L2 加顶；记录可重演。

上版已用完整十局排位验证换边、单组故障与五次 Elo 结算；该测试记录使用上版规则。新旧比赛包的实现摘要不同，核验时需要使用各自的代码。

策略在独立持久子进程运行，启动预算 5 秒；回调预算为 20 ms CPU 和 200 ms 墙钟，父进程同时轮询 Windows 或 Linux 进程内存，超过 256 MiB 时终止。两个进程收齐决定或判错后，内核才推进共同边界。预算是本机教学初值；轮询不是容器硬配额。

本机早期 180 秒基线实跑用时约 15 秒，父进程 CPU 约 12 秒；完整未压缩比赛包约 74 MB，浏览器加载整局也会占用相应内存。这是一次单机测量，不是并发容量结论。程序直接从文件逐帧落盘，不需要先把整局快照留在父进程内存里。

`--trusted-code` 仅用于已审查队内代码，服务限本机回环访问。策略与服务同一操作系统用户，可能访问该用户可读文件、环境及网络；限时子进程不构成安全沙箱。不要公开端口、反向代理或接收匿名代码。上线前需要验证非特权容器或虚拟机、外网和宿主目录隔离，再另做账号权限和压测。

地图提供规则尺寸的 2.5D 教学模型，作业位、路网和局部安放位置是平台假设。车辆碰撞、视觉、实车控制与 TR 策略不在本版。动作参数待实车标定，整摞建塔的正式认可与计分待核项见[规则裁决](../05_规则裁决与计分.md)。
